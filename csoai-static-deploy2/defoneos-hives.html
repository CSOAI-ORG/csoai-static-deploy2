What is a Hive?

A hive is a sovereign AI base — a single, self-healing, Ed25519-signed AI node that:

  • Spawns agents from a 6-type taxonomy (worm, dragonfly, hornet, killer bee, sage, guardian)
  • Communicates via SIGIL pheromones (8 op types P/V/M/Q/C/H/S/A, TTL 48h, hash-chained)
  • Participates in the 33-node BFT council (22-of-33 quorum on every escalation)
  • Has its own domain specialty (one of 12: Land/Sea/Air/Space/Cyber/EW/Underground/Cognitive/Bio/Quantum/Arctic/Urban)
  • Self-heals via heartbeats (5-min cycles) and SIGIL-backed checkpoints
  • Reports to the sovereign substrate (SOV3 hub at :3101, sovereign substrate at :3200)

Each hive is a single Python process running on a single VM (or container) with a dedicated Ed25519 keypair. The keypair is the hive's identity — every SIGIL it emits is signed with that key. If the key is rotated (90-day cycle per PQC schedule), a new SIGIL chain anchor is emitted.

BFT Council Mechanics

Quorum Rules (Castor-Liskov PBFT)

The 33-hive council uses Practical Byzantine Fault Tolerance (PBFT), originally described by Castro & Liskov (1999, OSDI). The quorum threshold of 22-of-33 tolerates up to 10 malicious or faulty nodes (f = ⌊(n-1)/3⌋ = 10) while maintaining consensus on the system state.

Council composition (n=33): - 33 sovereign hives - 22-of-33 quorum (≥ 2f+1 where f=10) - Byzantine tolerance: up to 10 malicious nodes - Liveness: ≥ 22 honest nodes respond within 5s - Safety: no two conflicting decisions can both reach quorum Vote types: - Red-line trip (kinetic, personal-surveillance): 22/33 + 1 veto from Guardian - Human-oversight override: 22/33 standard - Autonomous kill-switch: 15/33 (faster, no Guardian veto required) - Charter amendment: 27/33 (supermajority, 3-day cool-off) - Standard operational: 12/33 (low-stakes) or single-hive (trivial)

Council Chair Rotation

Council chair rotates every 24 hours, deterministically chosen from the 33 hives by the formula chair = (current_unix_day mod 33). The chair has no special power — its role is to sequence the vote agenda and emit the council SIGIL (type=C). All votes are public and SIGIL-signed; any hive can audit any other hive's voting record.

SIGIL Pheromone Comms

Inter-hive communication uses SIGIL pheromones — Ed25519-signed, hash-chained, TTL-bounded messages. There are 8 op types:

OpNameUseTTL
PProposalNew action proposed, awaiting BFT vote48h
VVoteCouncil member casts vote (for/against/abstain)24h
MMessageInformational, no action required48h
QQueryRequest information from a specific hive1h
CCommitCouncil decision, binding actionPermanent (anchored Bitcoin every 1K)
HHeartbeat5-min liveness signal10m
SSnapshotState checkpoint (every 100 H sigils)Permanent
AAlertRed-line trip, immediate attention1h, escalated to BFT if not ack'd

Each SIGIL includes: timestamp, op type, sender hive ID (Ed25519 pubkey hash), recipient (broadcast or targeted), payload (JSON), Ed25519 signature, previous-SIGIL hash (chain). At 1 SIGIL/second aggregate, the chain grows by ~86,400 entries/day. Every 1,000 entries, the chain head is anchored to Bitcoin via OP_RETURN (cost ~$5 per anchor).

What This Page Is Not

  • The 33-hive count is architectural: 33 is the design target for the BFT council (one hive = one vote). The current live hive count is ~12 (T2 in the table above). The remaining 21 hives are at T0/T1 (schema or reference impl) and are not yet running in production.
  • No hive is currently battle-tested with real operational data. All T2 hives run on synthetic test data. Live operational deployment requires a customer contract and a deployment environment — neither exists yet.
  • The "1Hz SIGIL rate" is the target per-hive emission rate. The current aggregate rate is lower (the 49K SIGILs to date have been accumulated over ~6 months of development + testing, not at full production rate).
  • The "10 malicious nodes tolerated" is the PBFT theoretical maximum. In practice, the council is run by the same single team (CSOAI engineers), so there is no realistic adversary model where 10 of 33 nodes are malicious. The BFT architecture is future-proofing for multi-operator deployments (e.g. UK MOD + DASA + NATO DIANA each running their own hive subset).
  • Bitcoin anchoring is operational in testnet (4 anchors emitted to date) but not yet on mainnet (cost & irreversibility review pending — see defoneos-key-rotation.html).
